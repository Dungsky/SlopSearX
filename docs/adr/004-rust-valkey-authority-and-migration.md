# ADR 004: Valkey authority and Rust cutover

- **Status:** Proposed for F02 maintainer acceptance
- **Scope:** Rust Rewrite durable state, shared caches, workflow execution and production cutover
- **Decision authority:** Maintainer direction in the Rust rewrite case study and issue #881; acceptance is the merged F02 PR
- **Date:** 2026-10-15
- **Depends on:** ADR 003 and accepted F01 state inventory

## Context

Valkey is the only shared authority. The current implementation stores search caches, snapshots, research jobs/budgets/leases, saved definitions/schedules/reports/events, staged plans, receipts, OAuth credentials/tokens, browser sessions/memberships/idempotency, rate windows and health/audit state. F01 records their key prefixes, TTLs, serializers and error distinctions in `inventory/core-contracts.json` and `core-contracts.md`. The research job record and lease token are authoritative; ready/recent indexes are repairable hints. `ResearchJobStore.save_if_owned` checks token and writes atomically. Saved definitions similarly use revision and lease fencing. A Rust process with only an in-process lock cannot reproduce this across replicas.

## Decision: drain, migrate and one execution owner

Choose **drain-and-migrate with an exclusive writer**, not concurrent mixed-version Python/Rust writers in one authoritative namespace. This is a deployment and ownership choice; Rust may still read legacy record formats. No Python and Rust worker may claim the same queue, renew the same lease, issue the same OAuth transition, mutate the same workflow, or write the same cache namespace at the same time. Do not split a live tenant between runtimes. A production canary is the first bounded traffic stage **after** the exclusive handoff; the retired Python deployment remains stopped. Traffic beyond the admitted canary limit is held or rejected according to the G05 approved maintenance packet, then increased only after observations pass. Isolated staging/replay may use a sanitized Valkey clone before this handoff; it must not duplicate live provider requests or scheduled mutations.

For the rollback observation window, Rust writes the existing key names, record fields and JSON/ID bytes for every durable namespace unless a specific forward **and reverse** migration has passed. A writer must not emit an unknown enum/state, new required field, changed digest/ID, incompatible TTL or altered Lua ownership protocol into a rollback namespace. Any new internal Rust representation stays behind the durable DTO boundary. An additive field is not assumed safe: Python reader behavior must be measured. Existing opaque IDs retain their byte identity. Versioned caches may move to a new namespace only after they are classified disposable and recomputable; they must not leak into durable artifact IDs. The registry of namespace/format decisions is `docs/rust-rewrite/architecture/state-compatibility.md`; it cannot silently replace the F01 machine inventory.

### Ownership and dispatch authority

An authority-bearing workflow command may dispatch only after its applicable tenant/grants, engine policy, filter constraints, idempotency identity, expected revision, budget and deadline are validated. Budgeted workflow reservations are durable and atomic before dispatch; ordinary anonymous public search retains its accepted policy inputs and best-effort cache behavior without mandatory tenant or budget persistence. The durable worker receives a lease token and records an attempt with sufficient identity to account for an ambiguous remote outcome. A result commits only if the same token still owns the lease and the record revision/current cancellation/deadline state permits it, in one Valkey transaction or Lua script. A lost lease forbids a stale commit; it does not prove the remote provider did not run. Budget charged for an unknown provider outcome is not refunded. Retries append attempts and preserve previous evidence/cost. The job record is authority; queue, due and recent indexes can be rebuilt from bounded scans. All replicas share the same Valkey time/atomic admission rule where a quota depends on wall time; monotonic process clocks remain local deadline helpers only.

**Evidence** is immutable once admitted: snapshot content/ID, research attempt outcomes, receipts, manifests, lineage and historical measurement bytes are append-only or write-once by ID. **Execution state** is mutable under revision/fence: queued/running/terminal job status, current lease, budget reservation, cancellation, schedule next-due, OAuth code/token use, browser session generation and idempotency claim. A rendering or MCP projection may derive a view but cannot rewrite canonical evidence. Repairable indexes are neither evidence nor authority. Expiry has two clocks: logical visibility/authorization horizon and backing-key retention for reconciliation; a retained key does not authorize access after logical expiry. Readers return distinct `missing`, `expired`, `unavailable`, `forbidden` and valid-empty outcomes where the current contract does, instead of collapsing them to `None`.

### Cutover procedure and gates

| Phase | Owner and precondition | Evidence and stop condition | Recovery class |
| --- | --- | --- | --- |
| Inventory/prepare | State owner records all F01 namespaces, TTLs, records, indexes, leases, due queues, cursors, tombstones, idempotency, OAuth/session keys, cache keys, and exact serializers; release owner captures sanitized backup and tested restore | Source/target census by tenant and key type; exact bytes/IDs; restore drill with measured RTO/RPO | Restore only for data loss before new writes; snapshot restore after new writes would discard them and is not ordinary rollback |
| Drain | Operations owner stops new admission and schedulers, waits for or explicitly classifies active leases/ambiguous calls, then stops **all** Python mutation owners | Zero active valid old leases, no progressing old workers, bounded outstanding calls recorded and charged; abort if ownership cannot be proved | Rollback by resuming Python before Rust writes |
| Forward compatibility | State owner migrates only approved incompatible namespaces using idempotent, resumable scripts; preserves backup and journal | For each record compare completeness, decoded accuracy, timestamps/TTL timeliness and cross-index consistency; any mismatch stops cutover | Rollback via tested reverse migration **before** Rust writes, otherwise roll-forward or restore with explicit lost-write analysis |
| Rust handoff/canary | Release owner enables one Rust writer generation, then bounded real traffic with Python stopped | Owner generation/fence, accepted/rejected requests, queue progress, OAuth/session journeys, provider-call budget and all reconciliation dimensions; abort on duplicate owner or invalid writer | Rollback to Python only after Rust is drained and reverse-read/reverse-migration of **all Rust-created records** passes |
| Expand/close window | Release owner increases traffic under G05 thresholds; state owner continues reverse-read checks until rollback window ends | Reconciled source/target IDs, TTLs, indexes and successful restarts/scale; close only after G04/G06/G07 gates, rollback observation and explicit owner acceptance | After irreversible schema retirement, roll-forward; tested backup restore is a separate data-loss decision |

The exact maintenance duration, canary fraction, RTO/RPO, thresholds and observation window are G05 release inputs requiring owner acceptance before G07. F02 does not invent them. Cutover fails closed if the packet has no capacity to hold/reject non-canary traffic or cannot prove exclusive ownership. A Valkey outage during durable mutation/authorization denies the operation; best-effort search cache may degrade according to its existing contract. A successful cache miss does not stand in for an unavailable durable store.

### Compatibility window and recovery proof

The compatibility window opens only when the Rust candidate can decode the full legacy corpus and write bytes that the pinned Python rollback image accepts. It closes only when G04 has tested both directions including **Rust-canary-created** records, G06 exact artifacts and G07 observation pass, no old executable/worker remains active, and the release owner accepts a recorded roll-forward/restore plan for any subsequently new-only format. Before each rollback, stop Rust admission/workers, reconcile completed/ambiguous attempts and all newly written records, run the pinned Python readers **without mutation** over those records, then start the old writer generation only if the full reverse-read set passes. Rollback never means simply restoring a pre-cutover snapshot: that loses writes received during canary. If reverse read fails, keep Rust stopped or read-only while fixing/migrating forward under the incident plan; do not let Python overwrite unreadable state.

For every namespace, F05/F07/W00–W11/T04/T09 define a specific legacy reader, Rust reader, Rust writer, Python reverse reader or reverse migrator, and test fixtures. G04 rehearses interruption at every phase, lease expiry/reclaim, current and stale writers, mixed key versions, missing/expired/unavailable outcomes, a multi-process real-Valkey race, and fresh versus stale session/OAuth credentials. No same-namespace dual writer is permitted as a shortcut to zero downtime. A future mixed-version design requires a superseding ADR and real-Valkey proof of identical atomic scripts, serializers, fencing, budget and rollback semantics.

## Consequences and open risks

This decision accepts a bounded admission interruption for the production handoff, with its limit subject to the G05 packet. It keeps one authoritative Valkey service and allows a true code rollback while compatible bytes remain proven. It does not promise exactly-once remote provider execution, zero downtime, or lossless restoration from a snapshot taken before Rust writes.

| Risk | Accountable role | Must close before |
| --- | --- | --- |
| A legacy reader silently accepts a changed field but changes meaning | State owner | F05 format fixtures and G04 reverse-read rehearsal |
| Lease TTL or Lua script behavior differs under contention | Workflow/state owner | W02/W04/W11 multi-process real-Valkey tests; G02 |
| Global keys/quotas make a split canary unsafe | Release owner | G05 traffic packet; no split namespace/owner without new ADR |
| Backup restore cannot preserve accepted canary writes | Release owner | G04 measured restore RTO/RPO and G07 recovery acceptance |
| New-only records after window close preclude old-image rollback | Integration/release owner | Explicit close event and roll-forward plan before G08 retirement |
