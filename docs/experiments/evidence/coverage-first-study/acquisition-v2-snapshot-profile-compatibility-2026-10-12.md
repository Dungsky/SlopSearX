# Acquisition snapshot profile compatibility finding

The acquisition/2 producer writes a versioned snapshot index and artifacts with `coverage-native-pool-snapshot/2` schemas and an explicit `coverage-acquisition-profile/2` identifier. `scripts/coverage_live_acquire.py:verify_pool_snapshot_index` defaults `expected_execution_profile` to the legacy profile. That default validates the `/1` index and artifact schemas. The explicit profile/2 verifier path accepts the v2 schemas and validates the 13-operation inventory.

Two consumers omitted the execution-profile argument: `scripts/coverage_late_registration.py` in `build_postacquisition_materials` and `scripts/coverage_selector_input_map.py` in `build_selector_input_map`. Their calls therefore selected the legacy default even when passed a v2 acquisition result. The late-registration consumer produced the observed terminal refusal documented in the [outcome](acquisition-v2-late-registration-terminal-2026-10-12/README.md); the selector input-map path was not reached in that stage. A separate read-only check using the explicit profile/2 setting verified the index and all 13 operation records. That compatibility check did not rerun or rescue the stage.

The adjacent orchestration validators already derive and pass the profile from the registered acquisition manifest. The corrective source change should propagate that same registered profile through both consumers, preserving strict schema/version checks. It should not reinterpret v2 artifacts as v1 or relax any acquisition, registration, quality, or admission condition. This is a source-compatibility finding, not evidence of a scientific outcome.
